# Creare un cluster EKS su AWS (pattern `eks`)

Genera il modulo `modules/eks` (con il sottomodulo `modules/eks/addons`) e, per ogni ambiente, gli stack `envs/<env>/kubernetes` (cluster, nodi di sistema, add-on gestiti, ruoli Pod Identity, risorse di Karpenter) e `envs/<env>/kubernetes-addons` (provider `helm`: AWS Load Balancer Controller, Karpenter con il chart delle CRD, KEDA). I workload (manifest, chart delle applicazioni, NodePool di Karpenter) sono compito di kybes, non di questo comando. Prima di scrivere o modificare codice carica le regole della skill `kynfra-architecture` (`SKILL.md` e `references/aws.md`, sezione `eks`). Il kit si trova in `tools/kynfra/plugins/kynfra/` (nel repository del plugin: `plugins/kynfra/`); di seguito `<kit>`.

1. **Leggi lo stato**: `.kynfra/config.json` (`infra_root`, `project`, `region`, `environments`, `accounts`, `tags`, `iac`) e cosa esiste già sotto `infra_root`: `envs/*/kubernetes`, `envs/*/kubernetes-addons`, `envs/*/network`, `envs/shared/ecr`, `bootstrap/`, i `tfvars` esistenti. Il pattern richiede `network` (lo stack kubernetes legge `vpc_id` e `private_subnet_ids` dal suo stato) ed `ecr` (registry delle immagini dei workload): se mancano, proponi di generarli prima con `/kynfra:create-network-infra-aws` e `/kynfra:create-ecr-infra-aws`. Se `bootstrap/` manca, segnala che il backend S3 dello stato deve esistere prima dell'`init` degli stack e proponi `generate.py --pattern bootstrap`.
2. **Un solo giro di domande**, solo su ciò che manca:
   - ambienti da generare (es. `dev,prod`; gli stessi input valgono per tutti, prod ha i propri default più restrittivi);
   - `admin_principals` (obbligatorio): ARN di ruoli o utenti IAM dell'account, separati da virgola, che diventano amministratori del cluster con access entry e `AmazonEKSClusterAdminPolicy`; deve includere l'identità con cui il DevOps applica lo stack `kubernetes-addons` (puoi leggerla con `aws sts get-caller-identity`, solo se l'utente lo chiede);
   - `public_endpoint_cidrs`: vuoto (default, solo endpoint privato) oppure CIDR espliciti separati da virgola (es. `203.0.113.0/24`), mai `0.0.0.0/0`; con l'endpoint solo privato lo stack `kubernetes-addons` va applicato da una rete che raggiunge la VPC (VPN, Direct Connect, bastion);
   - `kubernetes_version` (default `1.36`, l'ultima supportata sia da EKS sia dai chart bloccati del kit);
   - node group di sistema: `node_instance_types` (default `m6i.large,m5.large`, x86_64), `node_min_size`/`node_desired_size`/`node_max_size` (default 2/2/4, in prod 3/3/6);
   - `log_retention_days` (default 90, in prod 365, obbligatorio almeno 365) e `deletion_protection` (default `true` in prod, obbligatoria).
   Gli ambienti già generati non vengono sovrascritti.
3. **Genera**:

   ```bash
   python3 -B <kit>/scripts/generate.py --pattern eks --provider aws --env dev,prod --var admin_principals=arn:aws:iam::123456789012:role/devops [--var public_endpoint_cidrs=203.0.113.0/24] [--var node_instance_types=m6i.large,m5.large]
   ```

   Il generatore non sovrascrive file esistenti salvo `--force`, che chiede l'utente. Per vedere le differenze con una versione più recente del kit (anche le versioni dei chart di `versions.json`): `--upgrade`.
4. **Personalizzazioni** solo con gli strumenti di modifica dei file, mai con redirect o `sed -i` da shell: ogni scrittura passa dalle regole. Altri node group: nuove voci nella mappa `node_groups` del blocco `module "eks"` di `envs/<env>/kubernetes/main.tf` (`instance_types`, `min_size`, `max_size`, `desired_size`, facoltativi `ami_type` e `disk_size`). Versioni fissate degli add-on gestiti: `addon_versions` nello stesso blocco (altrimenti la più recente compatibile con la versione del cluster). Ruoli Pod Identity dei workload: `aws_iam_role` con trust `pods.eks.amazonaws.com` (condizioni sui session tag di namespace e service account) e `aws_eks_pod_identity_association`, mai IRSA né chiavi. Mantieni `endpoint_private_access = true`, l'endpoint pubblico solo con `public_endpoint_cidrs`, `encryption_config` dei Secret, i cinque tipi di log del control plane, `authentication_mode = "API"` con `bootstrap_cluster_creator_admin_permissions = false`, `metadata_options { http_tokens = "required" http_put_response_hop_limit = 1 }` nel launch template e il `version` fisso di ogni `helm_release`.
5. **Controlla**: `python3 -B <kit>/scripts/arch_check.py . --external` e correggi la causa di ogni finding (mai soppressioni inline). Se mancano strumenti esterni proponi `/kynfra:tools`. Non eseguire mai `helm` (salvo `template`, `lint`, `show`) né `kubectl` (salvo `get`, `describe`, `explain`).
6. **Riepiloga** in poche righe:
   - file creati (modulo, sottomodulo `addons`, stack `kubernetes` e `kubernetes-addons` per ambiente) e output dello stack kubernetes: `cluster_name`, `cluster_endpoint`, `cluster_ca`, `cluster_security_group_id`, `node_security_group_id`, `node_subnet_ids`, `node_kms_key_arn`, `karpenter_queue_name`, `karpenter_node_role_name`, `pod_role_arns`;
   - costi: control plane EKS per ora e per cluster (più l'extended support se la versione esce dallo standard), istanze del node group di sistema e quelle create da Karpenter, tre chiavi KMS, log del control plane, coda SQS ed EventBridge (trascurabili);
   - comandi che esegue il DevOps con le sue credenziali (tu non li lanci): prima gli stack network dell'ambiente ed `envs/shared/ecr`; poi `cd <infra_root>/envs/<env>/kubernetes && terraform init && terraform plan -out=kubernetes.tfplan && terraform apply kubernetes.tfplan`; poi, con un'identità di `admin_principals` e una rete che raggiunge l'endpoint, `cd <infra_root>/envs/<env>/kubernetes-addons && terraform init && terraform plan -out=kubernetes-addons.tfplan && terraform apply kubernetes-addons.tfplan` (o `tofu`);
   - passi manuali: con l'endpoint solo privato, accesso dalla VPC (VPN o bastion) con la 443 ammessa nel security group `cluster_security_group_id`; un `NodePool` e un `EC2NodeClass` di Karpenter a carico dei workload (kybes), con `spec.role = karpenter_node_role_name`, subnet `node_subnet_ids`, security group `cluster_security_group_id` e `node_security_group_id`, `httpTokens: required` e dischi cifrati con `node_kms_key_arn` (esempio nel README del modulo); con il pattern `elb`, `TargetGroupBinding` verso `target_group_arn` e la porta dei pod ammessa in `node_security_group_id` dal security group del load balancer; scaler SQS di KEDA con `identityOwner: operator` sulle code `<progetto>-<env>-*`; destroy in ordine inverso (NodePool, `kubernetes-addons`, `kubernetes`) e in prod prima `deletion_protection = false` con un apply.
