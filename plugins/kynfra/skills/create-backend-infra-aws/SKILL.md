# Creare il backend di un progetto kybes su AWS (pattern `backend`)

Genera il modulo `modules/backend`, lo stack `envs/<env>/backend` per ogni ambiente e, una volta sola, lo stack condiviso `envs/shared/apigw-account` (ruolo CloudWatch di API Gateway: impostazione unica per account e regione), leggendo il contratto di kybes: `schemas/openapi.yaml` (operazioni e `x-kybes-handler`), `services/<contesto>/functions/<nome>` (Lambda: runtime e handler dal manifest), `services/<contesto>/ms/<nome>` (microservizi su EKS), `jobs/<nome>` (job KEDA; `jobs/<nome>/job.yaml` con `schedule: "cron(...)"` per i job a calendario) e `schemas/db` (RDS Proxy). Non è uno scheletro: ogni elemento del progetto ha la sua infrastruttura, e la regola `api-coverage` blocca finché schema e infrastruttura divergono. Prima di scrivere o modificare codice carica le regole della skill `kynfra-architecture` (`SKILL.md` e `references/aws.md`, sezione `backend`). Il kit si trova in `tools/kynfra/plugins/kynfra/` (nel repository del plugin: `plugins/kynfra/`); di seguito `<kit>`.

1. **Leggi lo stato**: `.kynfra/config.json` (`infra_root`, `project`, `region`, `environments`, `accounts`, `tags`, `iac`, `kybes`, `public_routes`) e cosa esiste già sotto `infra_root` (`envs/*/backend`, `envs/*/network`, `envs/*/secrets`, `envs/*/kubernetes`, `envs/shared/ecr`, `bootstrap/`). Senza la sezione `kybes` in config il comando non parte: la config è protetta, la aggiunge l'utente (`"kybes": {"root": "."}`) o reinstalla kynfra nel repository kybes. Leggi lo schema OpenAPI e le cartelle `services/` e `jobs/` per capire cosa verrà generato.
2. **Requires**: servono `network` e `secrets` dello stesso ambiente (lo stack legge VPC, subnet private, `secret_arns` e `kms_key_arn`; lo stack secrets non legge mai il backend); con microservizi o job anche `eks` (stack `kubernetes` e `kubernetes-addons`) ed `ecr` (stack condiviso `envs/shared/ecr` con un repository per microservizio, `<contesto>-<nome>`, e per job, `<nome>`). Se mancano proponi di generarli prima con i rispettivi comandi (`/kynfra:create-network-infra-aws`, `/kynfra:create-secrets-infra-aws`, `/kynfra:create-ecr-infra-aws` con `repositories=…`, `/kynfra:create-eks-infra-aws`); il generatore li riporta comunque in `missing_requires`. Se `bootstrap/` manca, segnala che il backend S3 dello stato deve esistere prima dell'`init`.
3. **Mappatura endpoint → handler**: ogni operazione indica il suo handler con `x-kybes-handler: <contesto>/functions/<nome>` (o `/ms/<nome>`); se manca vale la convenzione `/v1/<contesto>/...` quando il contesto ha un solo handler. Il generatore rifiuta le operazioni ambigue e gli handler inesistenti, e **non inventa mai un handler**: elenca all'utente le operazioni segnalate, chiedi a quale function o microservizio va ognuna e, dopo la conferma, aggiungi `x-kybes-handler` all'operazione nello schema (è un file di kybes: proponi la modifica, non decidere da solo). Una function senza runtime o handler deducibile (`package.json` con `engines.node` e `main`, `pyproject.toml` con `requires-python` e `handler.py`/`app.py`) va completata nel suo manifest.
4. **Un solo giro di domande**, solo su ciò che manca:
   - ambienti da generare (`--env dev,prod`, anche insieme);
   - `authorizer`: `lambda` (default; API Gateway REST non ha un authorizer JWT nativo: authorizer `TOKEN` su una Lambda che valida il JWT OIDC, codice del team nel pacchetto `authorizer/authorizer.zip`) con `oidc_issuer` (dedotto da `openIdConnectUrl` dello schema se c'è) e `oidc_audience` (obbligatorio con `lambda`), oppure `cognito` con `cognito_user_pool_arn` (niente `oidc_audience`);
   - operazioni con `security: []` nello schema: restano senza authorizer solo se sono anche in `public_routes` della config (file protetto: lo modifica l'utente), altrimenti il generatore le lascia protette e lo segnala. `public_routes` in `handlers.auto.tfvars` è una fotografia della config al momento del comando: dopo una modifica di `public_routes` in config si rigenera;
   - con `schemas/db`: `db_instance_identifier` (istanza RDS esistente con l'autenticazione IAM attiva; il database è fuori dalla v1: RDS Proxy usa IAM end-to-end, `default_auth_scheme = "IAM_AUTH"`, senza segreti) e `db_engine_family` (`POSTGRESQL` di default o `MYSQL`, anche per MariaDB; SQL Server non è ammesso perché l'autenticazione IAM end-to-end di RDS Proxy non lo supporta);
   - con microservizi o job: `kubernetes_namespace` dei service account (default `default`);
   - `log_retention_days` (90; 365 in prod, obbligatorio), `throttling_rate_limit`/`throttling_burst_limit` (100/200), `waf_enabled` (obbligatorio in prod), `deletion_protection` dell'NLB (obbligatoria in prod).
5. **Genera**:

   ```bash
   python3 -B <kit>/scripts/generate.py --pattern backend --provider aws --env dev,prod [--var oidc_audience=<client-id>] [--var oidc_issuer=https://login.example.com] [--var authorizer=cognito --var cognito_user_pool_arn=arn:aws:cognito-idp:<regione>:<account>:userpool/<id>] [--var db_instance_identifier=<istanza>]
   ```

   `handlers.auto.tfvars` (`handlers`, `routes`, `public_routes`), `jobs.auto.tfvars` (`jobs`) e `kybes.auto.tfvars` (`kybes_root`, `openapi_path`, `has_db`) si **rigenerano a ogni comando** (in `regenerated`), anche senza `--force`: non modificarli a mano, si modifica il progetto kybes e si rilancia il comando. Gli altri file esistenti non vengono sovrascritti salvo `--force`, che chiede l'utente; per le differenze con una versione più recente del kit: `--upgrade`.
6. **Personalizzazioni** solo con gli strumenti di modifica dei file, mai con redirect o `sed -i` da shell: ogni scrittura passa dalle regole. Nei `terraform.tfvars` dello stack: `context_secrets` (segreti dello stack secrets leggibili per contesto o per job, es. `{ ordini = ["db"] }`: policy identity sugli ARN, nessun valore nelle variabili d'ambiente), gli input del giro di domande. Nel blocco `module "backend"`: `lambda_memory_size`, `ms_target_port`, `ms_health_path`, `ms_listener_ports`, `job_visibility_timeout_seconds`, `waf_rate_limit`, `authorizer_runtime`, `db_iam_user`. Mantieni `timeout = 10` delle Lambda (oltre i 10 s kybes usa un microservizio), `tracing_config { mode = "Active" }`, i log group con retention e KMS, `access_log_settings` con `correlationId`, il `body` letto dallo schema (`yamldecode(file(...))`: lo schema resta l'unica fonte, niente route scritte a mano nel modulo).
7. **Controlla**: `python3 -B <kit>/scripts/arch_check.py . --external` e correggi la causa di ogni finding (mai soppressioni inline); `api-coverage` deve essere verde. Se mancano strumenti esterni proponi `/kynfra:kynfra-tools`.
8. **Riepiloga** in poche righe:
   - lock dei provider: il primo stop gate (o la CI) crea un `.terraform.lock.hcl` in ogni stack nuovo; l'agente non può scriverli (`protected-files`): ricorda all'utente di committarli;
   - file creati e rigenerati, handler, route e job trovati nel progetto; output dello stack: `api_domain_name`, `api_origin_path` (vuoto: stage `api`, URL `https://<id>.execute-api.<regione>.amazonaws.com/api/<percorso base>/...`, e il behavior `/api/*` della SPA inoltra il percorso così com'è), `base_path` (da `servers[0].url`), `api_id`, `stage_name`, `invoke_url`, `lambda_function_names`, `artifacts_bucket`, `artifact_keys`, `queue_urls`, `dlq_urls`, `pod_role_arns`, `service_accounts`, `vpc_link_id`, `ms_target_group_arns`, `db_proxy_endpoint`, `db_proxy_security_group_id`, `workload_repository_urls`;
   - costi: API Gateway (richieste), Lambda, WAF dove attivo, NLB con microservizi, RDS Proxy (per vCPU del database), SQS, KMS, CloudWatch Logs;
   - comandi che esegue il DevOps con le sue credenziali (tu non li lanci): prima network, secrets e (con ms o job) kubernetes, kubernetes-addons ed `envs/shared/ecr`; una volta per account (salta se un altro progetto dello stesso account l'ha già applicato: ruolo `kynfra-apigateway-cloudwatch`) `cd <infra_root>/envs/shared/apigw-account && terraform init && terraform plan -out=apigw-account.tfplan && terraform apply apigw-account.tfplan`; poi `cd <infra_root>/envs/<env>/backend && terraform init && terraform plan -out=backend.tfplan && terraform apply backend.tfplan` (o `tofu`);
   - codice: kynfra genera l'infrastruttura, non il codice; il codice della Lambda authorizer (validazione del JWT OIDC con `OIDC_ISSUER` e `OIDC_AUDIENCE`, pacchetto `authorizer/authorizer.zip`) lo scrive il team, come le function;
   - passi manuali: la CI carica gli zip delle Lambda in `artifacts_bucket` (`<contesto>/<nome>.zip`, `authorizer/authorizer.zip`) prima del primo apply e passa `artifact_sha256s` a ogni build; con `schemas/db` ammettere nel security group del database la sua porta dal security group `db_proxy_security_group_id`; verificare che l'istanza abbia `iam_database_authentication_enabled = true` e creare nel database l'utente `db_iam_user` per l'autenticazione IAM (le Lambda e il proxy si collegano come quell'utente con IAM end-to-end): in PostgreSQL `CREATE USER app; GRANT rds_iam TO app;`, in MySQL/MariaDB `CREATE USER 'app'@'%' IDENTIFIED WITH AWSAuthenticationPlugin AS 'RDS' REQUIRE SSL;`, più i privilegi sulle tabelle; per i microservizi un `TargetGroupBinding` per target group e i service account di `service_accounts` nel namespace; il valore dei segreti lo inserisce il DevOps fuori da Terraform; dopo ogni modifica di `services/`, `jobs/` o dello schema si rigenera con questo comando.
